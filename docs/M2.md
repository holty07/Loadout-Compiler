# M2 — balance harness

Scope: sweep runner (`harness/sweep.gd`), report generator, a generated loadout
matrix (every legal combination at each tier plus a random sample of
mixed-tier builds), a hill-climb search over the matrix, and a deliberately
crude debug renderer — boxes and labels, no design tokens, no polish,
disposable code thrown away at M4. No data-only balance tuning yet — that
is M3.

The debug renderer isn't optional scope-creep: without it, the first moment
anyone can watch this game is M4, which is most of the way through the
build — far too late to discover the core loop is inert. See
`docs/plan.md`'s *Testing points* and *Why the debug renderer exists*.
Budget roughly a day for it and build it knowing it's thrown away; it must
never become a dependency of the real M4 shell.

## Exit criterion

```bash
godot --headless --script harness/sweep.gd -- --matrix harness/loadouts.toml --seeds 2000 --out reports/
```

completes in under two minutes on 8 cores for 50 loadouts × 2,000 seeds, and
commits a report artefact under `reports/` with win rate, clear rate per
depth, time-to-kill spread (p10/p50/p90) per enemy archetype, and
first-choke attribution as a distribution.

The debug renderer has no automated exit criterion of its own — it's a
throwaway tool for the human testing points in `docs/plan.md`, not a tested
deliverable. It just needs to open a recorded run and step through it.

## Design decisions made to fill gaps in `docs/plan.md`

- **Performance required a real fix, not just the log-stripping mitigation.**
  A single-process 2,000-seed benchmark ran at ~12.5ms/run — extrapolating
  to 50×2,000 gave ~1,250s, which even perfect 8-way fan-out (~156s) misses
  the 120s budget. Stripping event-log emission alone (`fire`/`jam`/`hit`,
  and `spawn` once TTK stopped needing it — see below) barely moved it
  (~12.5ms → ~12.4ms): the real cost was re-deriving each module's scalars
  from nested `dict.get("provides", {}).get(...)` chains on every tick.
  `sim/pipeline.gd` now pre-extracts those scalars once per run
  (`Pipeline.new_state()`), which alone roughly halved per-run cost
  (~12.5ms → ~6.5ms). Verified byte-identical log hash on the fixture seed
  before/after — a pure perf refactor, no `sim/VERSION` bump for that part.
- **Enemy instance ids became `<archetype>@<spawn_tick>#<index>`**, globally
  unique across the whole run (not reset per wave), so `harness/report.gd`
  can recover time-to-kill straight from a `kill` event's own subject with
  no need to correlate a separate `spawn` record. This *is* a log-shape
  and hash-changing behaviour change — `sim/VERSION` bumped 2 → 3. Still
  safe pre-golden-file (`tests/golden/` is still empty).
  `sim/log.gd`'s `SparseEventLog` (used only by `harness/sweep_worker.gd`)
  drops `spawn` too, since nothing in the report reads it — only
  `harness/dump_log.gd`'s full, non-sparse log keeps it, for legibility.
- **Measured sweep performance has thin margin, reported honestly rather
  than padded.** Two real 50×2,000 (100,000-run) runs on this 16-logical-core
  machine, 8 workers: 109.8s and 116.4s — both under the 120s budget, but
  only by 3–8%. The gap between that and the ~72.5s a naive
  "single-run-cost ÷ 8" projection would predict is most likely core
  contention (8 concurrent CPU-bound processes on a machine that may not
  have 8 fully independent cores once shared cache/memory bandwidth is
  accounted for), not something fixable in `sim/` without the Rust
  GDExtension escalation `docs/plan.md` explicitly gates on profiling
  showing the simpler mitigations insufficient — which this doesn't, yet.
- **Fan-out is OS processes, not in-process threads**, per `docs/plan.md`'s
  own wording ("one headless instance per core"). `harness/sweep.gd` spawns
  one `harness/sweep_worker.gd` per core via `OS.create_process()`, sharded
  by loadout index (round-robin) so no cross-shard merging of raw samples
  is needed within a loadout — only whole per-loadout summaries and one
  raw grand-accumulator (for statistically correct pooled TTK percentiles;
  averaging each worker's already-computed percentiles would be
  percentile-of-percentiles, which is wrong).
- **The matrix is 4 uniform-tier loadouts (all four slots at the same tier)
  plus 46 seeded-random mixed-tier loadouts**, deduplicated and
  legality-checked via `sim/loadout.gd`, giving exactly the 50 the exit
  criterion benchmarks against. `harness/generate_matrix.gd` is the
  generator; `harness/loadouts.toml` is its committed output, regenerated
  (not hand-edited) when `/data` changes. Written as `[loadout.<key>]`
  sections rather than `[[loadout]]` array-of-tables, since
  `tools/toml.gd` doesn't parse the latter.
- **The report has two tiers**: `overall` (pooled across every run in the
  sweep — win rate, clear rate per depth, TTK percentiles per archetype,
  first-choke distribution, damage-taken share) and `per_loadout` (the same
  shape per loadout), so M3's per-build targets (median loadout win rate,
  any module's share of winning builds, distinct clearing builds) are
  answerable straight from the committed artefact without re-running
  anything.
- **First-choke attribution is the first `module_offline` event in a run**,
  mapped to its module's slot via `/data`; a run with no `module_offline`
  event at all (died to raw damage before any subsystem choked) counts as
  `"none"` — a real, informative bucket, not an error case.
- **Buffer/heat occupancy histograms (from `docs/plan.md`'s fuller "rig"
  description) are deliberately out of scope for M2.** They're not in this
  milestone's actual exit criterion, and the event log's closed kind enum
  doesn't carry continuous per-tick state — only discrete events. Building
  a separate instrumentation channel just for this wasn't justified by
  what's gated here; revisit at M3 if tuning turns out to need it.
- **The debug renderer has no spatial data to show** — M1 deliberately has
  no positional simulation, so this isn't a top-down view, it's a
  scrubbable timeline: a slider over tick range, a running state readout
  (`harness/debug_replay.gd`, tested headlessly), and a scrolling list of
  colored box+label rows, one per event up to the current tick. **Its
  rendering has not been visually verified** — this environment has no
  display. It loads and runs for several frames headlessly with no script
  errors (`godot --headless --quit-after 5 harness/debug_renderer.tscn`),
  but open it yourself in the editor before trusting the layout.
