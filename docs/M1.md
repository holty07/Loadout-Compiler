# M1 — sim core

Scope: the pipeline (feed → chamber → cooling → targeting), heat and buffer
model, per-room encounter resolution, facility and route generation, and the
top-level run loop. Enough `/data` for four modules per slot and four enemy
archetypes. No balance tuning against the targets table — that is M3. No
sweep runner — that is M2. No shell.

## Exit criterion

1,000 randomly generated *legal* loadouts run to completion: no crashes, no
non-terminating runs, no negative-resource states. A fuzz test over malformed
loadouts fails gracefully with named errors.

```bash
godot --headless --script tools/run_tests.gd
```

exits 0, and within that run `tests/test_run_volume.gd` and
`tests/test_loadout_fuzz.gd` both pass.

## Design decisions made to fill gaps in `docs/plan.md`

The plan fixes the tick order and the four-stage pipeline shape but doesn't
pin every mechanical detail. Where a call was needed, the option chosen is
the one that keeps the sim data-driven, integer-only, and faithful to the
locked tick order — nothing here invents a new RNG draw or a hardcoded
balance number.

- **Module `provides` fields are slot-specific**, extending the schema
  example in `docs/plan.md`: feed → `supply_rate` (Fx units/100 ticks),
  `buffer`; chamber → `cycle_interval` (ticks), `damage_per_round`; cooling →
  `dissipation` (heat/tick); targeting → `targets_per_cycle`,
  `hit_chance_percent`. `tools/schema/module.json` is extended to match, as
  optional properties.
- **Each module's `failure.mode` is mechanical for the slot it's declared
  on**: feed declares `starve` (informational — the actual `jam` event is
  attributed to the feed module id when the chamber can't cycle, so the run
  report can later name the true bottleneck); chamber declares `jam`, with
  `threshold` as the consecutive-jam count before the chamber itself goes
  `module_offline` for a penalty window; cooling declares `overheat`, with
  `threshold` as the heat level above which cooling shuts off for a penalty
  window (a deliberate positive-feedback risk); targeting declares
  `offline`, with `threshold` as the heat level above which targeting stops
  converting fired rounds into hits (chamber still fires and spends
  buffer/heat — a wasted cycle, a legitimate trap-build shape for M3).
  Penalty windows are data (`tuning.toml` → `[penalties]`), not GDScript
  literals.
- **No spatial/positional simulation.** The locked tick order in
  `docs/plan.md` has no step for enemy movement or engagement range, so none
  is invented. `behaviour.kind` and `engage_range` are stored as data for M1
  but not yet mechanically differentiated; all four enemy archetypes engage
  immediately on spawn and attack on their own `damage.interval` cadence.
  Kind-specific mechanics (rush closing distance, splitter spawning on
  death, shielded absorbing the first hit, etc.) are deferred to M3 content
  expansion.
- **Armour is a flat reduction after resist**, not a percentage; targeting's
  contribution to a hit is *breadth* (`targets_per_cycle`) and *chance*
  (`hit_chance_percent`), not armour penetration. Armour pierce is left for
  a later content pass rather than added now as an unused stat.
- **No run-report generator.** The event log carries everything a future
  report needs (jam/module_offline events are attributed to the module id
  that caused them), but producing the "what killed you" report itself
  isn't in M1's exit criterion and is deferred.
- **Interventions are plumbed in per the plan's open question**, at the
  recommended option: `Run.execute` takes `interventions: Array[{tick,
  action}]` alongside seed/loadout/route, validated (bad shape or
  over-budget fails the same way a malformed loadout does) and threaded
  through hashing by construction — even with an empty array, a run is a
  pure function of `(seed, loadout, interventions)`. Only one action,
  `vent` (zeroes accumulated heat), is implemented; unknown action strings
  are accepted as a forward-compatible no-op rather than an error, since the
  UI that spends the intervention budget doesn't land until M5.
- **Route generation is a straight line of `tuning.facility.room_count`
  rooms**, one candidate room type sampled uniformly by RNG per depth from
  whichever room defs cover that depth. Branching routes are an explicit
  open question deferred to M3 in `docs/plan.md`; nothing here forecloses
  it.
- **A `max_ticks_per_room` safety cutoff exists in `tuning.toml`.** Every
  room in the M1 data is tuned so real play never approaches it (worst-case
  damage output still clears the tankiest archetype in a small fraction of
  the budget), so hitting it would indicate a genuine data or logic bug, not
  a intended stopping condition — but its presence is what lets "no
  non-terminating runs" be an enforceable, testable guarantee rather than an
  assertion.
